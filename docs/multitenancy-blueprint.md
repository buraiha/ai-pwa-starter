# Multi-tenancy Blueprint

この文書は、スターターの認証なし単一利用者サンプルを、テナント分離されたPWAへ拡張するための基盤仕様です。実装済み機能ではありません。アプリごとのtaskで採用範囲と変更点を確定してから実装します。

## 1. 保護境界

- テナントはサーバーが認証済みセッションから確定する。
- クライアントが送った`tenantId`だけを認可根拠にしない。URLやJSONに含める場合も、セッションのテナントと一致するか検証する。
- 未認証、無効化済み利用者、別テナント、管理専用主体からの業務APIアクセスを拒否する。
- 認証が確定する前に、業務UI、Repository、自動保存、同期を起動しない。
- 開発用固定テナントへ暗黙にフォールバックしない。

## 2. 推奨するサーバーデータモデル

最低限、次の責務を分離します。

```text
tenants
tenant_users          tenant_idを持つ一般利用者
privileged_accounts   全体管理が必要な場合だけ、一般利用者と分離
sessions              subject、tenant、期限、失効状態
business_records      すべてtenant_idを持つ
audit_logs            認証・管理操作の追記記録
```

- 業務テーブルの主キーまたは一意制約に`tenant_id`を含める。
- 子テーブルも`tenant_id`を持ち、`(tenant_id, parent_id)`への複合外部キーで別テナントの親を参照できないようにする。
- IDが全体でUUID一意でも、検索・更新・削除条件には`tenant_id`を必須にする。
- 論理削除を同期する場合は`deleted_at`を保持し、配信済み確認前に物理削除しない。
- SQLite接続ごとに外部キーを有効化し、複数テーブル更新は同じトランザクションにする。

単一利用者が複数テナントへ所属する要件がある場合は、`tenant_users`へ直接`tenant_id`を置く構成ではなく、利用者と`memberships`を分離します。アクティブテナントの選択・切替・再認証規則も別taskで決めます。

## 3. セッションとブラウザ保存

- セッションIDは十分な乱数で作り、サーバーDBにはハッシュだけを保存する。
- Cookieは`HttpOnly`、`Secure`、適切な`SameSite`、`Path=/`を設定する。
- 状態変更APIはCSRF対策を必須にする。
- パスワードは平文保存せず、現在推奨されるパスワードハッシュと利用者ごとのsaltを使う。
- ログインIDと接続元の双方へレート制限を行い、認証・管理操作を秘密情報なしで監査記録する。
- LocalStorage、SessionStorage、IndexedDBへパスワード、セッションID、CSRFトークンを保存しない。

オフライン利用を許可する場合、IndexedDBへ保存できる認証コンテキストは次のような非秘密情報に限定します。

```text
subjectType
userId
tenantId
displayName
lastVerifiedAt
offlineExpiresAt
logoutPending
```

オフライン有効期間はアプリのリスクに応じて決めます。期限切れや無効化確認後はUIをロックしますが、利用者データを自動削除しません。オフラインログアウトは直ちにUIをロックし、再接続時には業務APIや同期APIより先にサーバー側ログアウトを完了します。

## 4. クライアントのテナント境界

- `TenantContext`相当の起動処理が、オンラインセッションまたは有効なオフライン認証コンテキストから現在の`tenantId`を確定する。
- 業務モデルは`tenantId`を持つ。
- Repositoryのすべての公開操作は`tenantId`を必須引数にする。
- Dexieは`[tenantId+id]`、`[tenantId+updatedAt]`、`[tenantId+syncStatus]`など必要な複合インデックスを持つ。
- 保存前に、親・子・添付ファイルの`tenantId`と関連IDが一致することを検証する。
- 一覧、取得、更新、削除でIDだけの検索を行わない。
- IndexedDBのデータベース自体をテナントごとに分ける方式を選ぶ場合も、切替時のopen/close、移行、容量、ログアウト時の保持規則を明示する。

## 5. APIと同期

- APIハンドラーは最初にセッションを認証し、そこから得た`tenantId`をStore層へ渡す。
- Store層の公開操作も`tenantId`を必須にし、SQLは必ず`WHERE tenant_id = ?`を含める。
- クライアント送信データの報告者・作成者を保持する場合、同期時のログイン利用者で暗黙に上書きしない。同一テナント所属を検証する。
- 受信データに別テナントが1件でも混ざる場合は部分適用せず失敗させる。
- サーバー受信で、端末の`pending`、`failed`、`sending`、`conflict`を上書きしない。
- 競合version、削除マーカー、冪等キー、同期カーソルはテナント境界の内側で評価する。
- 同じ同期操作で複数集約を扱う場合、原子的に確定すべき範囲をtaskで定義する。

## 6. 管理権限

- 全体管理主体とテナント一般利用者を同じ権限分岐に混ぜない。
- テナント管理APIは対象テナントへの管理権限を検証する。
- 全体管理機能をPWAのオフラインモードでは利用させない。
- 利用者無効化、パスワード初期化、権限変更、テナント作成を監査ログへ記録する。
- 利用者無効化または資格情報変更時に、該当セッションを失効させる規則を決める。

## 7. スターターからの変更箇所

| 現在の場所 | テナント対応時の変更 |
| --- | --- |
| `src/models.ts` | 全業務型へ`tenantId`、必要なら作成者スナップショットを追加 |
| `src/db/database.ts` | 認証コンテキストテーブルとテナント複合インデックスを追加、Dexie version更新 |
| `src/repositories/` | 全公開操作へ`tenantId`を追加し、親子の所属を検証 |
| `src/services/` | セッション確認、テナント起動フェーズ、ログアウト待ち、認証付き同期を追加 |
| `src/App.tsx` | 認証確定前のローディング・ログイン・ロック画面を追加 |
| `server/` | tenants/users/sessions/auditと、tenant_id付き業務テーブルを追加 |
| `server.mjs` | Cookie、CSRF、レート制限、セッション由来認可を全業務APIの前段へ追加 |
| tests | 下記の分離・期限・競合マトリクスを追加 |

## 8. 必須テスト

- tenant Aの利用者がtenant BのIDを指定しても、取得・更新・削除・同期できない。
- 同じ業務IDが別テナントに存在しても相互に影響しない。
- 子データや添付ファイルを別テナントの親へ関連付けられない。
- 未認証、無効化、期限切れ、管理専用主体を拒否する。
- オフライン有効期限の直前・直後、再起動、ログアウト待ちを確認する。
- オフライン認証コンテキストに秘密情報が含まれない。
- 同期APIがJSONの`tenantId`ではなくセッションのテナントを使用する。
- 受信に別テナントが混ざった場合、端末DBへ1件も適用しない。
- 同期中の追加入力、version競合、削除競合でも端末の未送信データを失わない。
- セッション失効後の再同期を拒否し、IndexedDBの業務データは保持する。

## 9. 推奨実装順序

1. テナント、利用者、パスワード、セッション、監査のSQLiteスキーマと単体テスト
2. Login/Logout/Session API、Cookie、CSRF、レート制限
3. PWA起動時の認証状態と、期限付きオフラインコンテキスト
4. 業務モデル、Dexie、Repositoryのテナント境界
5. 業務APIと同期APIのサーバー由来テナント認可
6. 管理機能とセッション失効
7. 自動テスト、HTTPS、複数ブラウザプロファイル、スマートフォン実機での総合確認

各段階を独立したtaskにし、前段の契約とテストが通ってから次へ進みます。
